## 먼저 말할 것 — 이 시스템이 뭘 주는가

매주 월요일 아침에 한 장. 세 칸이다.

| 칸 | 내용 |
|---|---|
| **주력** | 늘 떼오는 품목이 평년 이맘때 대비 지금 어떤지, 그 안에서 색·소재 구성이 어디로 움직이는지 |
| **뜨는 것** | 아직 작지만 빠르게 가속 중인 후보 10개 ← 이 프로젝트의 본체 |
| **꺾이는 것** | 컸는데 식는 중 — 신규 사입 중단·재고 소진 경보 |

**지금 한참 유행하는 것을 보여주는 게 아니다.** 그건 이미 늦다.
사입부터 촬영·등록·초기 반응까지 2~6주가 걸리니, 그만큼 먼저 잡아야 의미가 있다.

**말하지 말 것 두 가지.** "몇 개를 떼와라"는 아직 못 한다(④번 데이터가 있어야 한다).
그리고 네이버는 **수요(관심)만** 보여준다 — 동대문 공급 사정과 가격은 모른다.

## ① 시드 목록이 맞는가  *(덱 10장)*

매주 지켜볼 기본 품목. **여기서 모든 추천 후보가 나온다.**
`config/keywords.yaml` 과 동일. 역할이 둘로 나뉜다.

**발굴 시드 24개** — 연관어를 받아 후보를 만든다

| 분류 | 품목 |
|---|---|
| 상의 (9) | 가디건 · 니트 · **조끼** · 블라우스 · 셔츠 · 티셔츠 · 맨투맨 · 후드티 · **나시** |
| 하의 (7) | **바지** · **스커트** · **팬츠** · 청바지 · **반바지** · 슬랙스 · 레깅스 |
| 아우터 (7) | 패딩 · 코트 · 자켓 · 바람막이 · **집업** · **점퍼** · 무스탕 |
| 원피스 (1) | 원피스 |

**관찰 전용 7개** — 후보를 만들지 않고 "지금 수요가 어떤지" 만 본다

> 트렌치코트 · 롱스커트 · 와이드팬츠 · 미니스커트 · 카고팬츠 · 블레이저 · 점프수트

앞 다섯은 **상위 품목이 알아서 품는다** — 트렌치코트는 코트의, 미니스커트는 스커트의
세부 품목이라 따로 발굴할 필요가 없다. 뒤 둘은 찾아봐도 세부 품목이 거의 안 나온다.

**물을 것**

- 안 떼오시는 품목이 섞여 있나 (레깅스·바람막이는 애슬레저 쪽이라 취급 안 하실 수도)
- 꼭 봐야 하는데 빠진 품목이 있나
- **같은 품목인데 말이 둘인 것** — 어느 쪽을 쓰시나?
  `조끼 / 베스트` · `바지 / 팬츠` · `자켓 / 재킷`
  네이버에서는 서로 **다른 검색어**라 어느 쪽을 쓰느냐로 잡히는 양이 몇 배 갈린다

> **굵은 글씨 8개는 저희가 새로 넣은 것**이다. 네이버 데이터만 보고 정했다 —
> `조끼`가 `베스트`보다 5배 많이 물어오고, `스커트`·`바지`·`팬츠` 같은 기본 단어가
> 빠져 있었다. 실제로 안 떼오시는 게 있으면 빼면 된다.

**받아오면 할 일**: `config/keywords.yaml` 갱신 → `config/taxonomy.yaml` 의 `item` 축과 정렬
(현재 `니트` 가 item 과 material 양쪽에 걸쳐 있는 충돌이 남아 있다)

## ② 후보 만드는 방식에 이견이 없는가  *(덱 11장)*

확인이라기보다 **오해를 막는 설명**이다. "AI가 유행을 지어내는 것 아니냐"는
의심을 먼저 끊어 둔다.

```
가디건  →  네이버 검색광고가 같이 검색되는 말을 월간 검색수와 함께 돌려준다
             니트 가디건   8,200   채택
             크롭 가디건   3,400   채택
             버건디 가디건 1,100   채택
             숄 가디건       260   제외 — 너무 작아 추세를 볼 수 없다
             가디건 코디  22,000   제외 — 이미 다 아는 말
             가디건 도매   1,900   제외 — 소비자 검색이 아니다
         →  채택된 것들의 주간 추이를 쌓는다
```

- **조합을 우리가 지어내지 않는다.** 사람들이 실제로 검색한 말만 쓴다
- 규모 필터는 **월 100~1만 건**. 위아래를 다 자른다
  (실측 근거: 연관어 1,200개 중 관련도가 규모와 반비례 — 월 0~100 구간 57%, 1만+ 구간 9%)
- 발굴 시드 24개 → 후보 수천 개 → LLM 선별 → 수백 개

## ③ 속성 축 11개로 옷이 설명되는가  *(덱 12장)*

`버건디 니트 가디건` 을 쪼개야 "무엇이 뜨는지"가 보인다.
`config/taxonomy.yaml` 의 `axes` 와 동일.

| 축 | 예시값 |
|---|---|
| 아이템 | 가디건 · 자켓 · 스커트 |
| 실루엣 | 오버사이즈 · A라인 · 벌룬 · 와이드 |
| 핏 | 크롭 · 루즈 · 레귤러 |
| 기장 | 미니 · 미디 · 롱 |
| 색상 | 버건디 · 올리브 · 파스텔 |
| 소재 | 니트 · 코듀로이 · 트위드 · 레더 |
| 패턴 | 체크 · 스트라이프 · 플로럴 |
| 디테일 | 퍼 · 퀼팅 · 시스루 · 러플 |
| 무드 | Y2K · 고프코어 · 올드머니 |
| 상황 | 데일리 · 출근 · 하객 · 여행 |
| 시대 | 90년대 · 2000년대 · 70년대 |

**물을 것**

- 실제로 떼오실 때 보시는 기준 중 이 11개로 설명이 안 되는 게 있나
- **계절**과 **가격대**를 넣을지 우리 쪽에서 고민 중이다 — 어떻게 보시나
- 반대로 안 쓰실 것 같은 축이 있으면 뺀다

> 계절 축은 실제로 비어 있는 상태다. 패션에서 계절은 지배적 변수라
> 셀러가 먼저 짚어줄 가능성이 높고, 그 답이 이 미팅에서 제일 값질 수 있다.

## ④ 데이터를 받을 수 있는가  *(덱 13장)*

**없어도 추천은 나간다.** 다만 "몇 개를 떼올지"는 이게 있어야 답할 수 있다.
아래가 요약이고, 판매자센터에서 항목별로 확인할 상세는 부록에 있다.

### 에이블리 판매자센터에서

먼저 **통계 메뉴에 엑셀 다운로드 버튼이 있는지**부터 확인. 여기서 갈린다.

| 항목 | 필요도 |
|---|---|
| 상품별 주간 판매수량 | 꼭 |
| 상품별 조회수 | 꼭 |
| **옵션명 (색상 · 사이즈)** | 꼭 |
| 찜 수 | 되면 |
| 상품명 · 등록일 · 가격 | 되면 |
| 몇 개월치까지 보이는지 | 확인만 |

> **색상은 꼭 따로.** 상품명에 `(3color)` 로만 적혀 있으면 "버건디가 떴다"를
> 자사 판매로 확인할 방법이 사라진다. 색상은 트렌드의 절반이다.

### 기억으로

다운로드가 안 되더라도 **이것만으로 검증이 된다.**

- 최근 1년 **크게 터진 상품 5~10개** — 품목 · 색상 · 떼온 시점 · 왜 샀는지
- **거의 안 팔린 상품 5~10개** — 품목 · 색상 · 떼온 시점 · 왜 안 됐다고 보는지

"그때 우리 시스템이 이걸 미리 잡았을까"를 맞춰 보는 유일한 답지다.

# 부록 — 판매자센터 확인 상세

친구분이 **my.a-bly.com 로그인 후 10분이면** 확인 가능한 항목들.
결과에 따라 Phase 3(캘리브레이션) 가능 여부가 갈린다.

> 조사 결과 에이블리는 셀러용 공개 API도, 공개된 판매자센터 매뉴얼도 없다.
> 모든 기능이 로그인 뒤에 있어 직접 확인하는 것 외에 방법이 없다.

---

## A. 꼭 확인할 것 (우선순위 순)

### A-1. 통계/분석 메뉴에 **엑셀(CSV) 다운로드** 버튼이 있는가  ★최우선
- 있으면 → Phase 3 가능. 시스템이 "참고용 신호"에서 "사입 결정 도구"로 올라감
- 없으면 → 화면 스크린샷 수기 입력 or 주문 내역 다운로드로 우회

확인 위치 후보: `통계`, `판매 분석`, `리포트`, `대시보드` 메뉴 안

### A-2. **상품 단위** 지표가 나오는가 (마켓 전체 합계 말고)

가능하면 **상품 × 옵션(색상·사이즈)** 까지. 색상이 빠지면 외부 트렌드와 맞출 축이 하나 사라진다 —
"버건디가 뜬다" 를 자사 판매로 확인할 방법이 없어진다.

필요한 최소 조합:

| 지표 | 왜 필요한가 | 필수? |
|---|---|---|
| 상품별 **판매수량** (일/주 단위) | 예측 타깃 그 자체 | ★필수 |
| 상품별 **조회수** | 판매보다 선행. 조기탐지 정답지 | ★필수 |
| 상품별 **찜(좋아요)** | 구매의도 선행지표. 조회수보다 강함 | 권장 |
| 상품 **등록일** | 신상품 반응 속도 측정 | 권장 |
| 상품 **가격** | 가격대별 반응 차이 | 권장 |
| 상품명 / 카테고리 | LLM 속성 매핑의 입력 | ★필수 |
| **옵션명** (색상·사이즈) | 색상은 트렌드의 핵심 축인데 상품명엔 "(3color)" 로만 적히는 경우가 많다 | ★필수 |
| 옵션별 판매수량 | 같은 옷도 색·사이즈별로 팔리는 속도가 다르다 | 권장 |
| 반품·교환 수량과 사유 | 사이즈 이슈 보정. 순판매 계산 | 권장 |

### A-3. **조회 가능 기간**
- 최소 **6개월**, 가능하면 12개월 이상
- 패션은 계절성이 지배적이라 1년치가 있어야 "작년 같은 시기 대비"를 볼 수 있다
- 3개월만 보관된다면 → **지금부터 매주 내려받아 쌓기 시작**해야 함 (이것만 해도 가치 큼)

### A-4. 다운로드 단위
- 일별인지 주별인지 월별인지
- 일별이면 최상. 월별만 되면 조기탐지 해상도가 떨어짐

## B. 있으면 좋은 것

### B-1. 주문 내역 다운로드 (정산/주문관리 메뉴)
통계 메뉴에 다운로드가 없어도, **주문 내역 엑셀**이 되면 그걸로 판매수량 시계열을 복원할 수 있다.
확인: `주문관리` 또는 `정산관리` → 기간 선택 → 엑셀 다운로드

### B-2. 광고 리포트
에이블리 광고를 집행 중이라면 `광고 성과 분석 → 엑셀다운로드`가 있다.
상품 단위 노출/클릭/전환이 들어있으면 조회수 대용으로 쓸 수 있다.
(단, 광고 집행 상품만 나오므로 전체 상품 커버리지는 안 됨)

### B-3. 플랫폼 전체 랭킹/인기 상품
내 마켓이 아니라 **에이블리 전체에서 뭐가 뜨는지** 보이는 화면이 있는가.
있으면 외부 신호 없이도 조기탐지가 가능해져서 네이버 의존도가 크게 줄어든다.

### B-4. ERP/솔루션 연동
사방넷·플레이오토 같은 통합관리 솔루션에 에이블리 연동이 열려 있는지.
(공개 자료로는 확인 안 됨 — 솔루션 업체에 직접 문의 필요)
연동되면 주문 데이터를 자동으로 끌어올 수 있다.

---

## C. 과거 사입 이력 (데이터센터 밖, 친구 머릿속)

시스템 학습에는 안 쓰더라도 **검증에는 이게 제일 값지다.**
- 최근 6~12개월 중 **크게 터진 상품 5~10개** — 품목, **색상**, 떼온 시점, 왜 샀는지
- **죽은 상품 5~10개** — 품목, **색상**, 떼온 시점, 왜 안 팔렸다고 보는지

> 색상까지 적어두면 속성 단위로 검증할 수 있다.
> "니트가 잘 나갔다" 와 "버건디 니트가 유독 나갔다" 는 검증 가치가 다르다.

이게 있으면 "우리 시스템이 그때 이걸 미리 잡았을까?"를 백테스트할 수 있다.
정량 데이터가 하나도 없어도 이것만으로 시스템의 쓸모를 1차 검증 가능.

## D. 하지 말 것

**에이블리 앱/웹 스크래핑.** 이용약관 위반 소지가 있고, 친구 계정이 걸려 있다.
파트너센터에서 합법적으로 받을 수 있는 경로를 먼저 다 확인한 뒤에 판단할 일이다.
