# 논의 정리 — 설계에 이르기까지

2026-10-21 ~ 10-22 · 이 프로젝트가 왜 지금의 형태가 되었는지에 대한 기록.
결론만 보려면 [ARCHITECTURE.md](ARCHITECTURE.md)를 보면 된다. 여기는 **왜 그렇게 정했는지**와
**중간에 뒤집은 판단**을 남긴다.

---

## 1. 출발점과 목표의 변천

| 단계 | 목표 | 무엇이 바뀌었나 |
|---|---|---|
| 최초 | "패션 트렌드 파악 + 변화 예측 체계" | 범위가 너무 넓음 |
| 1차 좁힘 | 패션의류 전체 · 예측 모델까지 풀스택 | 대상 확정 |
| 2차 좁힘 | **동대문 사입 의사결정 지원** | 용도가 생기면서 설계가 바뀜 |
| 최종 | **조기 탐지 + 포트폴리오 검증 설계** | 이중 목표 확립 |

"트렌드를 파악한다"에서 **"이번 주에 뭘 떼올지 정한다"** 로 목표가 내려오면서
산출물이 리포트가 아니라 **의사결정 리스트**가 되었다.

그리고 뒤늦게 드러난 사실 하나가 우선순위를 다시 뒤집었다 —
이건 친구를 돕는 일이기도 하지만 **취업 포트폴리오이자 프리랜서 사업 검증**이다.
둘이 충돌하면 포트폴리오를 우선한다. 사업 검증은 수개월이 걸리지만
포트폴리오는 수 주 안에 완성되고, 전자가 실패해도 후자는 남는다.

## 2. 조사로 드러난 사실들

### 2-1. 네이버 쇼핑 검색 API가 없어졌다 ★설계 전제를 바꾼 발견

- **2026-07-31 완전 종료, 공식 대체 없음.** 책·전문자료 검색도 동일
- 살아남은 것들은 **NAVER API HUB**(네이버클라우드)로 이관 — 주소·인증 헤더가 전부 바뀜
- developers.naver.com 신규 신청 종료, 기존 키는 2027-06-30까지 유예

**결과**: 상품명·가격·몰 같은 *상품 단위* 데이터의 공식 경로가 사라졌다.
그래서 이 시스템의 분석 단위는 상품이 아니라 **검색어 → 패션 속성**이 되었다.

### 2-2. 에이블리 셀러 데이터는 외부에서 확인 불가

공식 문서 / ERP 연동 / 판매자센터 세 방향으로 조사했으나:

- 셀러용 **공개 API 없음** (개발자 포털 자체가 없다)
- **공개 판매자센터 매뉴얼 없음** — `my.a-bly.com`은 로그인 벽, 공개 도움말 미연결
- 사방넷·플레이오토·이지어드민의 **에이블리 연동 여부 공개 자료로 확인 불가**
- 유일한 단서: 광고 관리에 `대시보드 / 캠페인통계 / 엑셀다운로드` 메뉴 존재.
  광고 집행 중이면 상품 단위 성과를 받을 가능성 — 단 광고 상품만 커버

**결과**: 더 파도 안 나온다. 친구가 로그인해서 직접 봐야 한다
→ [ABLY_DATA_CHECKLIST.md](ABLY_DATA_CHECKLIST.md)

### 2-3. 연관 키워드는 쇼핑인사이트가 아니라 검색광고 API

쇼핑인사이트에는 연관어 기능이 없다. **네이버 검색광고 키워드도구**
(`api.searchad.naver.com/keywordstool`)가 그 역할이고, developers.naver.com과
완전히 다른 시스템이라 이번 종료와 무관하게 살아있다.

얻는 것: 연관어 자동 발굴 + **월간 검색수 절대값**(PC/모바일 분리) + 경쟁도.
데이터랩이 상대값만 주는 문제를 여기서 보완한다. 광고 집행 없이도 신청 가능.

### 2-4. 신상마켓 — 아무도 안 보던 상류 신호

조사 중 발견. 동대문 B2B 플랫폼으로 도매가 하루 3.5만 개 신상을 올리고
소매 회원 35만 8천 명이 본다. 셀러면 가입 가능.

**도매가 지금 만드는 것이 2~4주 뒤 에이블리에 뜰 것의 예고편**이다.
기존 논의가 전부 소비자 하류(검색·클릭·랭킹)만 보고 있었다는 점에서 중요한 보완.

## 3. 핵심 설계 결정

### 3-1. 앵커 체이닝

쇼핑인사이트 `ratio`는 그 요청 안에서만 최댓값=100인 상대값이고
요청당 키워드 5개 제한이 있다 → **배치끼리 비교 불가**.

모든 배치에 고정 앵커를 1개 끼워 넣고 앵커 레벨로 나눠 공통 단위를 만든다.
슬롯은 4개로 줄지만 비교 가능성을 얻는다.

**단, 이 보정이 성립하는지는 가정이 아니라 측정으로 확인한다** —
같은 요청에 넣은 값(정답)과 따로 조회 후 보정한 값(추정)의 오차를 잰다.

### 3-2. 소급 백테스트

쇼핑인사이트는 2017-08-01까지 소급 조회된다. 두 가지 의미가 있다:

1. 이번 주에 처음 발견한 키워드도 **즉시 과거 시계열을 채울 수 있다**
2. 데이터를 쌓기 시작할 필요 없이 **오늘 백테스트가 가능하다**

### 3-3. 두 발굴 경로 비교 ★프로젝트의 중심

> LLM 웹 검색으로 발굴한 키워드와 검색광고 연관어로 발굴한 키워드 중
> 어느 쪽이 상승 트렌드를 더 일찍, 더 정확하게 찾아내는가?

같은 평가 지표(Lead Time, Precision@10) 위에서 경쟁시키고 백테스트로 승부를 낸다.
이것이 있고 없고가 프로젝트의 성격을 가른다 —
*"대시보드를 만들었다"* vs *"LLM의 비정형 탐색이 정형 API 대비 조기 탐지에 기여하는지 정량 평가했다"*.

### 3-4. 평가 지표를 교체

MASE·RMSE 같은 수치 예측 지표는 이 용도에 의미가 없다. 대신:

- **Precision@10** — 추천 10개 중 실제로 뜬 비율
- **Lead Time** — 피크보다 며칠 먼저 알렸나
- **False Alarm Rate** — 오탐률
- **하락 경보 적중률** — 악성재고 회피

**비용이 비대칭이기 때문이다.** 잘못 떼오면 재고 손실이 크고, 못 떼오면
기회손실인데 작다 → 정밀도 우선, 확신도 병기, **하락 경보를 상승 추천과 동등 취급**.

## 4. 뒤집은 판단 (정정 이력)

정직하게 남겨둔다. 틀렸던 것과 왜 틀렸는지가 설계의 일부다.

### 4-1. "수기 관찰을 최우선으로" → **철회**

**처음 주장**: 시계열은 지나간 주를 되돌려 수집할 수 없으니 오늘부터 쌓아야 한다.

**왜 틀렸나**: 쇼핑인사이트가 2017-08-01까지 소급 조회된다는 걸 과소평가했다.
과거 시점으로 돌아가 백테스트하면 **오늘 당장** 모델을 검증할 수 있다. 8주를 기다릴 필요가 없다.

**지금**: 수기 관찰은 유지하되 2순위. 역할도 바뀌었다 — 모델 검증용이 아니라
"검색 관심도 ≠ 에이블리 실판매" 간극을 메우는 보완재.
*(단 플랫폼 랭킹은 API가 없어 소급이 불가능하므로, 그 용도로는 여전히 지금부터 쌓아야 한다.)*

### 4-2. 호출 한도 "하루 1,000회" → **월 50,000회**

구 데이터랩 문서 기준의 수치였다. API HUB 기준은 월 50,000건 / 50 RPS.
수집 예산이 훨씬 넉넉해서 세그먼트를 나눠 돌릴 여유가 생겼다.

### 4-3. 초기 설계의 과잉 → **범위 축소**

처음엔 LightGBM 글로벌 모델, 분위 회귀, 다계층 앙상블까지 설계했다.
판매 데이터가 없는 단계에서는 전부 쓸 데가 없다. Phase 3으로 미뤘다.

**1차 산출물에 사입 수량을 넣지 않기로 했다.** 판매·원가·재고 없이 산출한 수량은
전부 가정 위의 숫자라 오히려 신뢰를 깎아먹는다.

## 5. 기각하거나 보류한 것

| 항목 | 판단 | 사유 |
|---|---|---|
| 커머스 랭킹 자동 수집 | **기각** | ToS/robots.txt 위험. 친구 계정이 걸려 있다. 수기 관찰로 대체 |
| 에이블리 앱 스크래핑 | **기각** | 동일. 합법 경로를 다 확인한 뒤에 판단할 일 |
| Google Trends | 보류 | pytrends 아카이브됨, `trendspy`도 불안정. 교차검증용으로만, 기본 OFF |
| Google Merchant API | 보류 | 계정 자격·국가 제한. 국내 소규모 셀러에겐 우선순위 낮음 |
| 멀티모달(상품 사진 분석) | Phase 2 | 텍스트 기반으로 먼저 MVP |
| LightGBM 수요예측 | Phase 3 | 판매 데이터 확보 후에만 의미 있음 |
| 크롤러 직접 개발 | **불필요** | 공식 API + LLM 웹 검색으로 충분. 크롤링은 목적이 아니라 수단이었다 |

## 6. 반복해서 확인된 원칙들

**LLM은 발굴하고 구조화한다. 판정은 정량 모델이 한다.**
LLM이 데이터를 보고 "이게 유행이다"라고 판단하게 두지 않는다.
리포트 단계의 LLM도 계산된 지표를 근거로 서술만 하고, 테이블 밖 숫자를 만들지 않는다.

**웹 기사는 공급측 의도다.**
매거진이 "올해는 버건디"라고 쓰는 건 브랜드가 밀기로 한 것이지
10대가 사고 있다는 뜻이 아니다. 웹 검색 결과는 **후보 발굴에만** 쓰고 판단 근거로 쓰지 않는다.

**계절성을 못 빼면 시스템이 평생 "겨울엔 패딩"만 말한다.**
STL로 계절 성분을 제거한 잔차가 진짜 신호다. 패션에선 이게 작업의 절반쯤 된다.

**검색과 쇼핑 클릭의 괴리가 정보다.**
검색은 느는데 쇼핑 클릭이 안 늘면 "화제성은 있으나 구매로 안 이어짐" = **사입 금지 신호**.

**세그먼트 필터는 선택이 아니라 기본값이다.**
타깃이 10~20대 여성인데 전체로 조회하면 40~50대 구매력에 묻힌다.

## 7. 가장 큰 미해결 리스크

**네이버 신호가 에이블리 고객을 대변하는가?**

10~20대 여성은 탐색을 네이버가 아니라 에이블리 앱·인스타·틱톡에서 한다.
네이버 지수가 올라도 에이블리에서는 이미 늦었거나 아예 안 올 수도 있다.

대응은 세 가지이고, 셋 다 **검증이 필요한 가설**이지 해결책이 아니다:

1. 세그먼트 필터로 네이버 안에서 같은 인구집단을 뽑아낸다
2. 친구의 파트너센터 통계를 정답지로 삼는다 (확보 가능한 경우)
3. 속성별로 상관을 측정해 상관 낮은 속성은 신호에서 제외한다

이 리스크가 해소되지 않으면 시스템은 "참고용 신호"에 머문다.
해소되면 "사입 결정 도구"가 된다. 차이가 크다.
