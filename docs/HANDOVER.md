## 1. 한 줄

에이블리 셀러에게 **매주 한 장짜리 사입 검토표**를 주는 시스템.
**설계와 실측은 끝났고 구현은 수집 계층까지** 와 있다. 탐지·모형은 아직 없다.

```
된 것    네이버 3종 수집 함수 · 앵커 체이닝 검증 · 시드 확정 · 설계서 4종 · 발표 덱
막힌 것  점유율 전환부터 — 코드가 없다
기다리는 것  셀러 미팅 (시드·속성축 확인, 판매 데이터)
```

## 2. 이어받는 사람이 할 첫 세 가지

순서대로. 1번은 막힌 것이 없어 **오늘 바로** 된다.

| | 할 일 | 왜 지금인가 |
|---|---|---|
| **1** | 분야 추이 수집 함수 + **점유율 전환** | 전 카테고리가 1년에 −43.5% 빠져서(발견 ⑤) 원지수로는 어떤 추세 계산도 틀린다. `detect.py` 의 `yoy` 가 지금 못 쓰는 상태인 것도 이 때문. **다른 모든 것의 전제** |
| **2** | 발굴 — v0 시드 20개 → 연관어 → 규모 필터 | 검색광고 20회. `searchad.get_keywords` 가 이미 있다 |
| **3** | 수집 + 캐시 — 격자 노드 ~720개 | 쇼핑인사이트 180회. `naver.get_trend` 가 이미 있다 |

3번까지 끝나면 `detect.py` 를 `share` 위에서 다시 돌릴 수 있고,
**"이번 주 뜨는 것"이 처음으로 숫자로 나온다.** 모형(M0~M3)은 그 뒤다.

전체 순서는 [PROGRESS.md](PROGRESS.md) "다음 작업 순서 (v3)" 표.

## 4. 키와 비밀

```
.env  는 gitignore 되어 있다. 커밋되지 않았고 커밋하면 안 된다
.env.example 에 필요한 변수 목록이 있다
```

| 키 | 상태 | 비고 |
|---|---|---|
| `NAVER_HUB_KEY_ID` / `KEY` | ✅ 발급됨 | 쇼핑인사이트·검색어트렌드 공용. 한시적 무료, **월 50,000건** |
| `NAVER_AD_CUSTOMER_ID` / `API_KEY` / `SECRET_KEY` | ✅ 발급됨 | 검색광고. 개인 광고주로 가입 가능(사업자번호 불필요) |
| `ANTHROPIC_API_KEY` | ⚠️ **다른 제품에서 쓰던 키** | 테스트용으로 빌려 쓰는 중. **실무 전환 시 새로 발급할 것** |
| KOSIS | 미발급 | 아직 불필요 |

> **계정이 바뀌면 `.env` 는 따로 전달해야 한다.** 레포에 없다.
> 네이버 키 2종은 각 콘솔에서 재발급 가능하고, Anthropic 키는 어차피 새로 받는 게 맞다.

## 5. 다시 밟지 말아야 할 지뢰

**여기가 이 문서에서 제일 값진 부분이다.** 전부 실측으로 확인한 것이고,
모르면 조용히 틀린 결과가 나온다. 번호는 [PROGRESS.md](PROGRESS.md) 실측 목록과 대응한다.

| | 하면 안 되는 것 | 왜 |
|---|---|---|
| ⑤ | 원지수로 추세를 계산한다 | 전 카테고리 1년 −35~44%. **점유율(÷ 분야지수)로 바꾸고 시작한다** |
| ④㉒ | 결측을 0으로 채운다 | `log(0) = −∞`. 다음 주가 무한대 급등으로 보여 **우리가 찾는 신호를 가짜로 만든다**. 바닥값 채우기는 맥락 특징에만 허용 (MODEL §4-1) |
| ⑬⑭ | 시드 단독 시계열을 품목 시장으로 쓴다 | 네이버는 **완전일치**다. `가디건` 은 가디건 수요의 10%뿐. `…가디건` 키워드를 **합산**해야 한다 |
| ⑲ | 격자 노드를 정렬해 정규화한다 | 수식어 순서를 가린다. `니트가디건` 41.2 vs `가디건니트` 1.2 |
| ⑯ | 성별을 키워드에 붙인다 | `여성가디건` 은 양자화 바닥에 눌린다. **조회 파라미터**로 건다. 그리고 남성어를 안 거르면 품목 시계열의 절반이 오염된다 |
| ⑳ | 검색광고에 힌트를 5개씩 묶어 보낸다 | 응답 한도를 나눠 써 뒤쪽이 잘린다. **스커트 15 → 단독 165.** 반드시 1개씩 |
| ③㉓ | 소규모 키워드 지표를 그대로 믿는다 | 양자화 바닥 `0.00437`. 월 140건이면 105주에 값이 47종뿐 — 증가율이 0인 주가 절반 |
| — | 군 집계를 그냥 더한다 | 멤버가 돌아온 것이 "급등"으로 읽힌다. **균형 패널로 비교** (MODEL §4-3 ④) |
| — | 백필 안 끝난 구간에 패널 행을 만든다 | 우리 공백을 데이터로 착각한다 (MODEL §4-2) |
| — | 폴드를 랜덤으로 나눈다 | 시차·시퀀스가 겹쳐 누수된다. 롤링 오리진 + **4주 공백** |

## 6. 알려진 결함

| 곳 | 내용 |
|---|---|
| `detect.py` | `yoy` 가 원지수 기준이라 **지금 쓰면 안 된다.** 점유율 전환 후 재가동 |
| `config/taxonomy.yaml` | `니트` 가 `item` 과 `material` 양쪽에 있다. **계절 축이 없다** (패션의 지배 변수인데) |
| `MODEL.md` §3-1 | 타깃은 4주 평균 비인데 자기회귀 항 `r` 은 아직 주 단위 점 대 점. 해상도 불일치 |
| 앵커 | 소형 규모대(0.05~0.5) 앵커 미정. 사다리 2·3단이 비어 있다 |
| 수확 수치 | 36개 중 16개가 API 상한(1,200)에 걸렸다. **하한치**이고 상한끼리의 서열은 못 믿는다 |

미결 항목 전체는 [MODEL.md](MODEL.md) 의 "미결" 과 [PROGRESS.md](PROGRESS.md) 의 "미결 설계".

## 7. 셀러에게 받아야 하는 것

프로젝트의 가장 큰 외부 의존이다. [CLIENT.md](CLIENT.md) 한 장을 그대로 전달하면 된다.

```
① 시드 목록이 맞는지        특히 조끼/베스트 · 바지/팬츠 — 어느 말을 쓰는지로 수확이 5배 갈린다
② 후보 만드는 방식 설명      확인이라기보다 "AI가 지어내는 것 아니냐" 를 막는 용도
③ 속성 11축이 맞는지        계절 축을 넣을지가 핵심 질문
④ 판매 데이터               판매자센터 엑셀 + 과거 사입 이력(터진 것·죽은 것 각 5~10개)
```

**④가 없어도 추천은 나간다.** 다만 "몇 개를 떼올지"는 답할 수 없고,
백테스트 정답지가 없어 시스템이 "참고용 신호"에 머문다.

## 8. 읽는 순서

```
1  이 문서
2  README.md                 전체 그림
3  docs/ARCHITECTURE.md      §0 목표 → §2 핵심 결정 셋 → §5 탐지 → §7 데이터 모델
4  docs/MODEL.md             §1 왜 패널인가 → §3-4 격자 → §4 결측

6  probes/                   위 수치를 직접 재현해 보고 싶으면
```

설계 문서가 길지만 **§0(이중 목표)만은 꼭 읽어야 한다.** 정확도가 아니라
**"안 맞을 때 안 맞는다고 측정할 수 있게 설계했는가"** 가 산출물이라는 전제가
모든 판단의 바탕이다. 이게 없으면 왜 M2를 건너뛰지 않는지, 왜 베이스라인을
모형보다 먼저 만드는지가 설명되지 않는다.

## 9. 마지막 당부

이 프로젝트에서 **설계를 바꾼 결정은 전부 실측에서 나왔다.** 추측으로 정한 것을
나중에 재서 뒤집은 일이 여러 번 있었고(PROGRESS 정정 이력 §4-1~4-5),
그때마다 바뀐 폭이 컸다. 1,557 → 3,350 같은 건 2배가 넘는다.

**새 가정을 세우면 먼저 재 보기를 권한다.** `probes/` 의 스크립트들이
그 방식의 예시다. 한 번 재는 데 10분이면 된다.
